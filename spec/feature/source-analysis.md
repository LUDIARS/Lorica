# Source analysis {#SPEC-LR-ANALYZE}

Human instruction (neco, 2026-11-12): detect code complexity; detect per function
whether it can run in parallel and whether memory barriers are needed; detect places
convertible to constexpr; the tools are used like assertions. This document covers
the shared extractor and the first analysis, complexity. Task:
`spec/tasks/2026-11-12-source-analysis.md`.

Purpose: a gate that runs where no compiler, build or clang is available (Python 3.9+
standard library only, as `tools/verify_binary.py`) and that leaves the analysed
code untouched. Limits and baselines live on the command line or in a JSON file,
never in the analysed sources (except an optional, reasoned suppression comment).

## Limits (read first)

The analyser is lexical. It is a heuristic gate, not a proof of anything.

- **No macro expansion.** Macros are not expanded; `#define` bodies are never read
  as code. Control flow inside a macro is invisible; a macro argument is read as
  written.
- **Preprocessor model.** No condition is evaluated except `#if 0` / `#elif 0`
  (dropped). For each conditional group, when every live branch is
  bracket-neutral for `() [] {}`, all branches are kept in source order (a union:
  metrics then count code that no single configuration compiles, and such
  functions are labelled "all preprocessor branches counted"). Otherwise only the
  first live branch is kept and the others are reported as "not analysed".
- **Templates as written.** Nothing is instantiated; types and overloads are not
  resolved; recursion is not detected.
- **Fail-closed, not complete.** What the scanner cannot classify becomes an
  *unparsed region* (file and line range) and no function or number is reported
  for it. Every report prints functions analysed, unparsed regions and lines not
  analysed.

Known silent misses (functions not reported and not inside an unparsed region),
measured on 5,577 libstdc++ 13 function definitions that clang-tidy-18 reports
(56 missed, all of them in these two classes):

| Class | Example | Measured |
| --- | --- | --- |
| Functions generated by a `#define` body | `functional_hash.h` `_Cxx_hashtable_define_trivial_hash`, `<charconv>` `to_chars` overloads, `<variant>` relational operators, `DEFINE_GETTER(...)` | 36 |
| Member functions of a class defined inside a function body: counted toward the enclosing function, not reported on their own | `~_Guard` in `basic_string.tcc`, `_Save_errno` in `ext/string_conversions.h` | 20 |
| Macro-hidden control flow (counted as a plain block or statement) | `FOREACH(x, c) { ... }`, `__try`/`__catch`, `assert(...)` | not a miss: lower counts |
| Logical operators inside a template argument list in a body | `__iter_swap<A && B>::` | higher count than clang-tidy |

For soundness use the real tools, not this one: the compiler and clang-tidy
(`readability-function-cognitive-complexity`, `readability-function-size`) for
metrics on one configuration with macros expanded; Clang `-Wthread-safety`
annotations and ThreadSanitizer for races; the compiler plus `static_assert` for
constant evaluation.

## Architecture

`tools/lorica_analyze.py` (command line) over `tools/lorica_analysis/`:

| Module | Responsibility |
| --- | --- |
| `lexer.py` | C++ tokens; directives (one per logical line) and comments (with lines) in side channels; raw strings, digit separators, alternative tokens, digraphs; never raises (errors become ERROR tokens, capped) |
| `preprocess.py` | The conditional-group pre-pass above |
| `extract.py` | Bracket matching, scope scanner, head classification, function records, unparsed regions. The API other analyses build on |
| `complexity.py` | Statement parser over a body and the metrics below |
| `gate.py` | Thresholds, baseline, suppressions |
| `sources.py` | Input selection and reading (UTF-8 with replacement, 8 MiB cap, never executed) |
| `report.py` | Text and JSON reports |

Extractor API: `analyse_text(path, text) -> SourceFile` with `tokens` (kept tokens),
`match` (index of the matching bracket or -1), `comments`, `functions`, `unparsed`,
`not_analysed`, `union_lines`. A `Function` has `name` (qualified by enclosing
namespaces and classes, template arguments dropped, `(anonymous namespace)`),
`kind` (function, constructor, destructor, operator, lambda bound at namespace
scope, macro-function such as `TEST(a, b) {`), `file`, `line` (of the name),
`start_line`, `body_line`, `end_line`, `parameters`, `specifiers` (constexpr,
consteval, static, inline, virtual, explicit, friend, template, const, noexcept,
override, final as written in the head), `in_class_body`, `in_header` (by
extension), `in_unnamed_namespace`, `body` (token indices of `{` and the last `}`,
the last handler of a function-try-block) and `lambdas` (each with the indices of
its `[`, parameter list and body). Functions overlapping an unparsed region are
dropped.

Scope scanner: only a `{` at declaration scope is classified, from the head
tokens since the previous `;`, `{` or `}`: namespace (also after a macro prefix),
`extern "C"`, class (class-key anywhere in the head, parentheses after the base
clause ignored), enum, requires-expression (after an operator, `=`, `(`, `,`,
`return` or `requires`), constructor initializer-list brace, function (the
declarator is the first `(` after a name followed by `{`, a cv/ref qualifier,
`noexcept`, `->`, `:`, `try`, `requires`, `=` or an all-caps macro), lambda bound
to a variable, initializer. A line `NAME(...)` with no `;` followed by a new
declaration is a macro statement, not part of the next head.

Unparsed regions are raised for: (1) a skipped brace block holding `;`, a control
keyword or `name(...) {` at its own depth; (2) a control keyword at namespace or
class scope; (3) bracket kinds that do not match; (4) an unclosed bracket or a stray
closer; (5) a head with parentheses but no declarator (K&R definitions, functions
returning function pointers); (6) a body the statement parser refuses; plus lexical
errors and broken `#if` structure.

## Metrics

Only the body is read: default arguments, `noexcept(...)` and requires-clauses in
the head are not counted. Lambda bodies and member functions of local classes
count toward the enclosing function, one nesting level deeper.

| Metric | Counting rule |
| --- | --- |
| cyclomatic | 1 + `if` + `else if` + `for` (also range-for) + `while` + `do` (once; its `while` is not counted again) + `case` + `catch` + `?:` + each logical `&&` / `||` (`and` / `or`). `else`, `default`, `switch`, `goto` add nothing |
| cognitive | SonarSource B1/B2/B3 without the recursion increment, as clang-tidy applies them: `if`, `?:`, `switch`, `for`, `while`, `do`, `catch` add 1 plus the nesting level; `else if`, `else`, `goto` add 1; each sequence of logical operators adds 1, on the expression tree (`a && b || c` 2, `a && (b && c)` 1, `a \|\| b && c \|\| d` 2); the bodies of those statements and of lambdas nest one level deeper; a ternary's branches nest until the next `,` or `;` or closing bracket; a condition of an `else if` is at the nesting of its body |
| nesting | Deepest nesting level of a statement body or lambda body (ternaries excluded) |
| parameters | Parameters of the declarator (`void` and an empty list are 0; a variadic `...` alone is not counted) |
| nloc | Lines from the first line of the declaration to the closing brace holding kept tokens (comments, blank lines, directives and dropped branches excluded) |

`&&` is a reference declarator, not an operator, when followed by `>`, `)`, `,`,
`...`, `]`, `;` or `=`, when preceded by `auto`, `const` or a builtin type, inside
a lambda parameter list, or in `T&& x =` / `T&& x{`. A fold over `&&` or `||` counts
as one operator (clang-tidy does not count it). Every increment is recorded with its
line and reason and printed under a failing function.

Agreement with clang-tidy-18 (IgnoreMacros on): Lorica 163 of 169 functions, the six
others explained (fold 1, `noexcept` in the head 1, macro expansion 2, single
configuration 2); libstdc++ 13, 5,353 of 5,521 matched functions (97.0%), every
difference in the classes macro expansion, `noexcept`/requires in the head, single
preprocessor configuration, clang-tidy's unbraced-nesting bug (`if (a) for (...)
if (b)` reports 3, braced 6), fold expressions, or the template-argument row above.

## Command line, thresholds, baseline, exit codes

```sh
python3 tools/lorica_analyze.py complexity [paths...] [--exclude GLOB]... [--compile-commands FILE]
    [--max-cyclomatic N] [--max-cognitive N] [--max-nesting N] [--max-parameters N] [--max-nloc N]
    [--baseline FILE] [--write-baseline FILE] [--strict] [--json] [--all]
```

Directories are walked recursively for `.c .cc .cpp .cxx .c++ .h .hh .hpp .hxx .h++
.inl .ipp .tcc .tpp`; a file named explicitly is read whatever its extension.
Nothing fails a run unless a threshold or a baseline is given. Gated metrics are
the ones with a threshold, or all metrics when only a baseline is given. A gated
value fails when the function is in the baseline and is worse than recorded (and
over the threshold, if any), or when the function is not in the baseline and is
over the threshold. `--write-baseline` records every metric of every function,
keyed `path::qualified-name(parameter count)` (`#2`… for further overloads of the
same arity), paths relative to the baseline file, `schema_version` 1.

| Exit | Meaning |
| --- | --- |
| 0 | Analysed and within limits |
| 1 | A threshold or the baseline is exceeded |
| 2 | Usage error, unreadable or oversized input, no file selected, unusable baseline, or (with `--strict`) any unparsed region |

Suppression, in a comment on a line of the declaration head (its first line to the
name): `// lorica-analyze: ignore(<check>[, <check>]) <reason>`, where a check is a
metric name or `complexity`. A suppressed finding is listed as suppressed with its
reason. A suppression without a reason suppresses nothing and is itself a finding.

Text output lists the coverage line, findings with contributing lines, suppressed
findings, unparsed regions, dropped branches, `--all` adds every function, and a
result line. `--json` (`schema_version` 1) holds `summary`, `functions` (metrics,
label, contributions), `findings`, `unparsed`, `not_analysed` and `errors`. There is
no markdown output.
